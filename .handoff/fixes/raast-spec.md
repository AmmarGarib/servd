RAAST QR TENDER + BANK-SMS MATCHING — BUILD SPEC (servd, 2026-10-12)

=== 0. BINDING DESIGN DECISIONS ===
D1 Tender. New PaymentMethod 'raast' and PaymentGateway 'raast'. 'keenu_qr' is RETIRED: kept in the Postgres enum (values cannot be dropped), never written by new code; old rows stay readable/reportable; an old keenu_qr sale is refunded by keenu_qr exactly as before. Ring-up (POST /pos/orders) and POST /pos/quote accept 'keenu_qr' only as a legacy alias of the digital rate (mapped to 'raast') so an offline-queued pre-deploy ring-up never 400s. Payments, settles, splits, quotes-for-payment and intents refuse it: 422 KEENU_QR_RETIRED 'Keenu QR is retired — take Raast QR or Card – Keenu'. Tills show exactly: Cash, Card – Keenu, Raast QR (+ Staff meal, Comp).
D2 Tax. lib/pricing Tender 'card' IS the digital tax group (card + Raast) -> Concept.taxRateCard (8%). Add 'raast' to CARD_TENDERS (keep 'keenu_qr' for legacy reads). No rename of Tender / PreBill.tender / fiscal payment.mode 'card'; UI labels say 'Card / Raast (8%)'. Never concept.taxRate.
D3 Sale vs truth. A Raast payment completes the sale at the till exactly like card (Payment.status 'paid' -> applyCoverageTx -> completeOrder -> FnF bill, the ONE fiscal sale document, loyalty; ledger at shift close / order.complete). 'provisional -> matched' is the reconciliation state of a new RaastReceipt row (bank-statement line = truth), never Payment.status.
D4 Ledger. Raast money debits the receiving BANK account's chart code (BankAccount.accountCode, snapshotted on the receipt as ledgerCode when recorded); Raast refunds credit that code; never 1030. Till sales post at the shift close (aggregated per code), non-till orders at order.complete. Every posting via postJournalEntry with the source document's tenantId, balanced, period-lock respected.
D5 SMS. Inside the existing POS connector module: PosConnector(kind 'raast') per company; its `enabled` = bank-SMS matching ON (default OFF; the CEO switches it on after a readiness check). Device tokens in a new table: secretBox ciphertext + SHA-256 lookup hash, created/rotated by CONNECTOR_ADMINS (admin, it). No new module id — Dev -> API stays exactly api_whatsapp + api_pos.
D6 Future bank API. Matching consumes a normalised BankCredit; the SMS parser is one producer. A later 'http' driver (RAAST_DRIVERS registry; webhook event 'raast.credit' on the existing /webhooks/pos/:token with HMAC; a dynamic QR whose bill reference = RaastReceipt.id) is another producer — no rework of intents, receipts, matching, ledger or UI. v1 builds the types + registry slot only, not the http driver.
D7 Gates (no GATED_PREFIXES change): till /pos/raast/* (CASHIERS, ungated like /pos/terminal/*), IT /connectors/raast/* (api_pos), finance /reconciliation/raast/* (reconciliation), receiving accounts /setup/* (FINANCE_TEAM), tender report /reports/by-tender (reports). The connector page gets bank-account choices from its OWN overview (IT cannot call /setup/bank-accounts).
D8 Company separation from the first commit: every new row carries tenantId from its source document (receipt <- order.concept.tenantId; device <- activeTenantId at creation; alert <- device.tenantId). Unique keys per company, except BankSmsDevice.tokenHash (a credential, globally unique like PosConnector.webhookToken — comment it). Foreign ids 404; cross-company attach on create 422; empty scope denies.
D9 Fraud rule. Raast is verified on the COUNTER device (merchant app / bank SMS), never the customer's screen; the till says so on every Raast screen and the cashier must tick an attestation when typing a reference (server-enforced `raastVerified: true`).
